# ISSUES

- SAM 3 の transformers ストリーミングモードは hotstart heuristics が無効になり, 誤検出・重複トラック増加が公式に警告されている.
- ROS One の apt リポジトリはローリングリリースの単一系列でスナップショット保証がない (対策として Docker イメージ保存を予定しているが未実施).
- コードレビューの未修正バグ: 上位10件のうち #1 (pdb), #9 (dockerfile), #7 (nerf 子プロセス死活未確認), #3 (`confs_gpu` リーク), #5 (percentile 空配列クラッシュ, 2026-07-03 修正), #8 (optimizeGPU の FAIL 非 return, 2026-07-03 修正), #6 (mconf 空配列 ValueError, 2026-07-03 修正) が修正済みで残りは未対応. 全一覧・判定・対応方針は `notes/REVIEW_findings.md` を参照. 特に優先度が高いのは zmq memcpy overread (#2, ただし該当経路は dead code のため実害は低い).
- 推論速度の未対応改善: 即効修正 4 件 (旧 Tier 0) は対応済み. 2026-07-03 の perf CSV 分析で壁時計の 52.7% が NeRF 同期待ちと確定し, 計画を"NeRF の同期待ちをなくす""毎フレームの処理を削る""長時間運用で速度を保つ"の 3 系統に再編した. 全項目一覧, 実施順, 修正ごとの確認方法, ベンチ結果, EfficientLoFTR の速度差分析は `notes/PERF_plan.md` を参照. 改善項目1 のうち NeRF warm-start (下記) のみ実装済み, 残りは未着手.
- NeRF warm-start (`reuse_weights=True`, `n_step_warm=300`) は速度優先でユーザーが採用を決定した (2026-07-03, コミット済み 28f25df). フルベンチで壁時計 -26.6% (683.1s→501.4s), nerf_wait 52.7%→35.9% を確認したが, アブレーションで速度改善のほぼ全部が学習反復数削減 (501→300) 由来と判明し, 重み引き継ぎ単体は速度にほぼ寄与せず精度に副次的残差を持つ. 軌跡整合ゲートは回転側で不合格 (median 1.885° vs 基準 1.33°, 超過率 71.7%) だったが, ユーザーは実用上問題ないと判断してこの回転差を許容した. ただし次の留保がある. (a) この回転差は baseline との相対差であり, GT に対する絶対精度が劣化したことを意味しない (どちらが正確かは GT なしには判定できない). (b) HO3D ADD/ADD-S による絶対精度確認は既定確定の必須条件ではなく, 余裕があれば実施する確認事項に格下げした.
- NeRF ラウンドの `runner_build` (毎ラウンドのモデル・オプティマイザ再構築) 廃止は, スモークベンチ (9 ラウンド) では有効だったが, フルスケール (111 ラウンド, octree/ray が大きい) では median 793ms→750ms とほとんど効かないことが判明した. `notes/PERF_plan.md` 改善項目1 の想定 (無害な runner_build 廃止) を修正する必要がある.
- `bundlesdf_node`/`sam3_segmenter` は `message_filters` の time-synchronized subscribe (rgb/depth/mask, `slop=0.05`) で繋がる別ノード構成のままである. この同期購読機構自体は, モックカメラストリーム (`mock_camera_stream.py`, ミルクデモ録画データ配信) による検証で実際に動作することを確認した (2026-07-05, 20フレームで19/19が姿勢を publish, 詳細は `notes/LOGS/log_ros_one_migration.md` 参照). ただし実際のカメラハードウェア (osx 側 RealSense) からのライブストリームでの検証はまだ行っていない. ノード統合の是非は, この実カメラハードウェア検証後に判断する方針は変わらない (保留事項の詳細は `notes/TODO.md` の「保留中」セクション, 検討の経緯は `notes/LOGS/log_ros_one_migration.md` 2026-07-03 参照).
- モックミルクデモデータの再生検証中 (2026-07-05), 処理された74フレーム中40フレームで BundleTrack 内部のトラッキング喪失 (`_cloud_down points#: 0 too small ... mark as FAIL`) が発生した. `~object_pose` publish バグとは別の問題であり, 原因は未調査. ミルクデモのモックデータ特有の追跡品質の問題である可能性がある.
- Docker イメージの再ビルド未実施: `docker/dockerfile` に `jq` を追加済みだが (2026-07-05), 実際のイメージビルドはまだ行われていない. 次回イメージビルド時にステータスバー表示 (モデル名/CTX/コスト) が正しく反映されることの確認が必要.
- delay-精度スイープ実行中 (2026-07-04〜05, `notes/PLAN_delay_accuracy_sweep.md`/`notes/TODO.md` 参照) に, バックグラウンド driver スクリプト方式で AP13 delay=12 を実行していたプロセスツリーが, Python トレースバック・CUDA OOM メッセージなど一切の痕跡を残さず消失し, 9時間気づかれなかった. OOM killer (cgroup memory.events で確認), GPU OOM, GPU ECC/Xid エラー, ディスク枯渇, セマフォリーク, timeout 強制終了, コンテナ/ホスト再起動, 他セッションの影響はいずれも証拠上否定されたが, コンテナの cgroup namespace 分離によりホスト側の状況を見る手段がなく, 根本原因は未特定のまま追跡不能と判断した. 対策として実行方式を「1セルずつ foreground・timeout 付き Bash で同期実行する」方式に変更し, 以降同種のクラッシュは再発していない.
- delay-精度スイープの MPM13 (`potted_meat_can`, 5本中1本) が全セット・全 delay で ADD 9.2〜11.4cm (他動画は概ね0.5〜3.0cm) に破綻する. frame1250〜1290帯で計15回中12回「NeRF worker process died」でクラッシュし (Python トレースバックなし), クラッシュ時のキーフレーム数が一貫して102〜113という狭い範囲に集中する (フレーム番号自体はばらつく). frame 固有のデータ破損ではなく, キーフレーム集合がこの規模に達したときの固定サイズバッファ境界か数値不安定性の可能性が高いが, 根本原因は未特定. set2 の delay=6,12 は3回再試行しても再現し恒久欠損として確定した (`data/bench_results/ho3d_sweep_opt/`).
- `docker/ros-one.dockerfile` の `opencv-python` バージョンが未固定 (`pip3 install ... opencv-python ...` にバージョン指定なし). 稼働中コンテナは調査の過程で意図せず `opencv-python==4.13.0.92`+numpy 2.2.6 に上がりBundleTrack の C++ 拡張 (numpy 1.26.4 ビルド) と ABI 不一致で SIGSEGV する事故が起きたため, `opencv-python==4.11.0.86`+`numpy==1.26.4` に手動で戻して回避したが, これは稼働中コンテナへの pip による一時対応にすぎない. Dockerfile 側は無修正のため, 次回イメージビルド時に最新版 (`5.0.0.93`, Qt `imshow` デッドロックの既知不具合版) が入り, 同じ SIGSEGV とデッドロックの両方が再発する懸念がある. `opencv-python==4.11.0.86` への固定を提案済みだがユーザー承認待ちで未着手.
- `sam3_segmenter` のセグメンテーション確認ゲート ("Accept segmentation? [y/n]:") の表示タイミングが不可解. 実機での目視では, 何か入力して Enter を押すまでプロンプトが画面に反映されないように見えるという報告があった. 標準出力バッファリングか, callback スレッドのログ出力との表示競合か, 他の要因かは未特定. `print(flush=True)` + プロンプトなし `input()` への変更を一度試みたが, 診断が不十分な対症療法との指摘を受け撤回済み (元の `input("Accept segmentation? [y/n]: ")` に復元済み).
- `bundlesdf_node` → `bundlesdf` へのパッケージ名リネーム作業中 (2026-07-06), `catkin_make` を複数回実行した際に `ros/bundlesdf/CMakeLists.txt` の `project(bundlesdf)` が意図せず `project(bundlesdf_node)` に書き換わる事象が2回発生した. `catkin_make` 実行直後の確認では正しい値のままであり, `catkin_make` 自体が書き換えている証拠はない. VSCode + CMake Tools 拡張機能がファイルを開いた際に自動で書き換えている可能性が高いが未確定. 実害は都度手動で直せば済むレベルで恒久対処はしていない (詳細は `notes/LOGS/log_ros_one_migration.md` 2026-07-06 参照).
