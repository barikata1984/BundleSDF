# 推論速度改善計画 (2026-07-03 再編)

オンライントラッキング (run_custom.py --mode run_video 相当) の推論速度を上げるための計画である.
参照・更新される文書として扱う (対応したら状態を更新する).

初版はコード調査に基づき, 修正候補を変更量の小さい順に Tier 0〜3 と分類していた.
その後 per-stage 計測 (perf CSV) で各処理の実測時間が確定し, 変更量ベースの分類は費用対効果の実態と食い違うことがわかった.
たとえば大レバーと見込んでいた C++ の同期処理は, 実測では数 ms しか占めていなかった.
そこで本版では, 計測結果に基づいて効果の大きい順に再編した.
旧 Tier の番号は対応する項目に併記する.

## 目標: 何をもって"速くなった"と数えるか

目標は, 新しいフレームの観測から実際に計算した姿勢を出力する頻度を上げることである.
同じ姿勢推定値を繰り返し出力する, フレームを間引くなど, 出力レートの数字だけを上げる変更は成果と数えない.

本計画の項目は, いずれも毎フレームの姿勢計算 (特徴マッチングとポーズグラフ最適化) を省略しない.
ただし姿勢の中身に影響しうる度合いは項目ごとに異なるため, 確認方法を 3 段階に分けて各項目に割り当てる.

- **確認不要**: 姿勢計算に一切影響しない変更 (ファイル書き出しの非同期化など). ベンチ数値の改善だけ確認する.
- **軌跡整合の確認**: 計算の順序や数値精度が変わりうる変更. 修正前後で `scripts/compare_poses.py` により姿勢軌跡を比較し, 差が現状の eloftr/loftr 間の差 (並進 median 0.16cm, 回転 median 1.33°) 以下であることを確認する.
- **絶対精度の確認**: NeRF の学習量や同期タイミングを変える変更. 軌跡整合に加えて, HO3D データセットの ADD/ADD-S (`benchmark_ho3d.py`, SM1 で完走確認済み [2026-07-03, ADD 2.20cm/ADD-S 0.98cm, 詳細は `notes/TODO.md` 参照], 条件を変えた比較自体は未実施) で劣化がないことを確認してから既定にする.

検収ベンチは `bash scripts/bench_milk.sh` (wall-clock, フレーム時間の median と p90, VRAM 推移).

## 計測でわかった現状

ミルク動画 1932 フレームを eloftr と loftr の両バックエンドで完走させ, per-stage 計測 (`BUNDLESDF_PROFILE=1`) の CSV を分析した.
CSV は `data/out_milk_{eloftr,loftr}/` 配下の `perf_main.csv`, `perf_nerf.csv`, `perf_nerf_train.csv`.

| backend | 壁時計 | fps | フレーム median | p90 | NeRF 同期待ち合計 | マッチャー段 median |
|---|---|---|---|---|---|---|
| eloftr | 683.1s | 2.83 | 163.5ms | 228ms | 359.9s (52.7%) | 61.8ms |
| loftr | 713.7s | 2.71 | 178.7ms | 247.6ms | 362.2s (50.7%) | 79.0ms |

両バックエンドの姿勢軌跡の差 (GT なしの相対比較) は並進 median 0.16cm / p90 0.45cm, 回転 median 1.33° / 最大 19.6° (低テクスチャ面での対称性の曖昧さが疑い).
以下の内訳は eloftr 側の数値だが, loftr も同じ構造である.

### 遅いフレームの正体は NeRF の同期待ち

フレーム時間の分布は二山に分かれ, p90 (228ms) を超える 194 フレームだけで壁時計の 60.0% を占める.
その 194 フレームの時間の 87.8% は NeRF 学習との同期待ちである.
待ちは 112 フレームに集中し (平均 3.2 秒/回), 合計 359.9 秒, 壁時計の 52.7% に達する.

以前の記録では裾を"NeRF 学習とグローバル BA"に帰属させていたが, 後半は誤りだった.
BA (ポーズグラフ最適化) は median 21.1ms, 最大でも 49.1ms で, 裾には寄与していない.

NeRF ワーカー側を見ると, 111 ラウンドの合計が 696.8 秒で壁時計とほぼ等しい.
つまり NeRF はセッション全体で休みなく回り続けており, それでもトラッキングに追いつけず, トラッキング側が待たされている.
現状の壁時計は NeRF のスループットで決まっている.
トラッキング自身の処理時間は 683 − 360 ≈ 323 秒しかなく, 待ちが完全になくなれば単独で 6.0fps 出る計算になる.

### NeRF ラウンドの内訳

1 ラウンドは median 6.11 秒かかる. 内訳は次のとおり.

- **学習ループ** (85.9%): さらに内訳は render 44.8% と backward 42.2% で, この 2 つが学習時間のほぼ全部を占める.
- **ランナー再構築** (13.0%, median 793ms): 毎ラウンド, NeRF のモデルとオプティマイザをゼロから作り直している.
- 残り (キーフレーム受信, シーン境界計算など) は合計 1% 未満.

また, 各ラウンド先頭の 50 反復だけが 812ms と, 以降の 50 反復あたり 439ms の約 2 倍かかる.
毎ラウンド約 370ms のウォームアップコストが乗っている (原因は未特定).

### 定常フレームの内訳

裾を除いた 1738 フレーム (median 163.5ms) の主な内訳は次のとおり.

| 処理 | median | 備考 |
|---|---|---|
| 対応点探索 (参照フレームと局所ペアの合計) | 約 85ms | 内訳: マッチャー推論 61.4ms, RANSAC 14.8ms, ペア列挙 6.3ms |
| 結果のファイル保存 | 21.6ms | 純粋な I/O. 15.8→28.9ms に増加中 |
| ポーズグラフ最適化 (BA) | 21.1ms | 横ばい |
| キーフレーム選択 | 15.5ms | 2.6→24.9ms に増加中 |
| フレーム構築 (デプス前処理を含む) | 4.2ms | 横ばい |

### 実行が進むほど遅くなる

フレーム median は序盤の 138ms から終盤の 180ms まで増加する.
増分はキーフレーム選択 (+22ms) と結果保存 (+13ms) でほぼ全部であり, マッチングと BA は横ばいである.
どちらもキーフレーム数に比例して伸びる処理であり, VRAM の単調増加 (17→26GB, 上限 32GB に接近) と同じく, キーフレームの蓄積に根がある可能性が高い.

## 改善項目 1: NeRF の同期待ちをなくす (壁時計の 52.7%)

待ちの機構は `bundlesdf.py:761-772` にある.
キーフレームの先行数が `sync_max_delay` (現在 3) 以上で, かつ NeRF ラウンドが実行中の間, 10ms 間隔のスピンで待つ.
NeRF が休みなく回っている現状では, ラウンド時間の短縮がほぼそのまま待ち時間の短縮になる.

各項目の状態は `[x]` 実施済み, `[ ]` 未着手で示す.
実施済みでも効果が見込みを下回った項目には, その旨をチェックの直後に明記する.

- [x] **学習反復数の削減, または前ラウンドの重みの引き継ぎ** (実装済み・採用決定, 2026-07-03): warm ラウンドで前ラウンドの NeRF 重みを引き継ぎ, 学習反復数を 501→300 に減らす.
  - **実装**: `config.yml` に `nerf_reuse_weights: True` / `n_step_warm: 300` を追加し, `bundlesdf.py:385` (warm-start), `bundlesdf.py:391-395` + `nerf_runner.py` の `train()` (`n_iters` 引数) を実装した. 実装過程で `nerf_runner.py:388,396` の潜在デバイスバグ (`reuse_weights=True` 経路が従来未使用だったため露見していなかった. `self.rays` がラウンド末尾で CPU に移るため 3 ラウンド目でデバイス不一致クラッシュ) を修正した.
  - **結果**: フルベンチで壁時計 683.1s→501.4s (−26.6%), 実効 fps 2.83→3.85 (+36.2%), `nerf_wait` 52.7%→35.9%, NeRF ラウンド median 6.11s→4.34s. フレーム median はほぼ不変 (163.5→161.6ms, 定常経路は無変更). ob_in_cam 1932 個で連続フレーム同一姿勢の繰り返しは 0 件であり, 見せかけの fps 向上ではないことを確認した. 一方, 軌跡整合ゲートは回転側で不合格 (baseline との回転差 median 1.885° > 基準 1.33°, 超過率 71.7%. 並進差は median 0.160cm で基準ぎりぎり通過).
    アブレーション (reuse+501, 反復数削減なしで重み引き継ぎのみ) では壁時計 718.7s (+5.2%, 改善ほぼ消失), 回転差 median 1.462° (基準をわずかに超過) となり, 速度改善はほぼ全部が反復数削減 (501→300) 由来で, 重み引き継ぎ単体の速度寄与は乏しく, 精度には副次的な残差 (基準超過分の約 1/4) が乗ることが分かった.

## 改善項目 2: 毎フレームの処理を削る (定常 median 163.5ms)

- [x] **結果保存の非同期化** (実装済み・ベンチ確認済み, 2026-07-03): `bundlesdf.py`. `saveNewframeResult()` は pybind 側で既に `py::call_guard<py::gil_scoped_release>()` 済み (`BundleTrack/pybind_interface/pybind_api.cpp:227`) だが, 単一スレッドで同期呼び出ししていたため待ちを解消できていなかった. C++ 定義 (`Bundler.cpp:964-1115`) を確認し, ディスク書き込みのみで `_newframe`/`_keyframes`/`_frames` 等の状態を変更しないことを確認 (バックグラウンド化の安全条件を満たす). 単一ワーカースレッド + `queue.Queue` で書き出しをオフロードし, フレーム順序保証のため次フレームの `self.bundler._newframe` 再代入 (`process_new_frame` 冒頭) の直前で `queue.join()` して前フレームの保存完了を待つようにした. `on_finish()` でも最終フレームの保存を待ってからスレッドを終了する. **結果**: async フルベンチ (`data/out_milk_eloftr_async/`, warm-start 適用済み baseline `out_milk_eloftr_item1` 比) で `save_result` median 21.99ms→0.01ms, フレーム total median 161.7ms→139.3ms (-22.4ms), 壁時計 501.4s→468.3s (-6.6%) を確認 (2026-07-03).
- [x] **キーフレーム走査の上限設定** (旧 Tier 3-1, 実装済み・ベンチ確認済み, 2026-07-03): `Bundler.cpp:298,509`. `selectKeyFramesForBA()` の `normal_orientation_nearest` 分岐 (共視性計算) が新フレームごとに既存の全キーフレームを走査する構造のため, キーフレーム数に対して O(N²) 化していた (序盤 2.6ms→終盤 24.9ms).
  - **検討した 3 案**:
    1. 走査に上限を設ける案 (却下): ミルク動画は回転を伴う撮影で古いキーフレームでも共視性が高くなり得るため, 直近 N 件に絞ると BA に使うフレーム集合が変わり軌跡精度に影響するリスクがあると判断した.
    2. コメントアウトされていた naive GPU 版 covisibility (`computeCovisibilityCuda`) の復活案 (却下): キーフレームごとに単発 GPU 呼び出しを行う方式. 400 フレームのスモークで実測したところ, キーフレーム 1 件あたりのメモリ確保・解放・同期のオーバーヘッドが支配的になり, CPU 版 (7.75ms) より遅い 19.2ms という結果になった. upstream 作者がコメントアウトしていた理由もこれと推測される.
    3. batched GPU 版 covisibility (採用): 共視性計算をキーフレームごとに個別に呼ぶのではなく, 全キーフレーム分をまとめて 1 回の GPU カーネル起動 (grid.z=n_kf) で計算する方式. 計算式自体 (法線と eye ベクトルの内積, 閾値判定) は CPU 版・naive GPU 版と同一で, 呼び出し回数のみを 1 フレームあたり 1 回に集約してオーバーヘッドを償却した.
  - **実装**: `CUDAImageUtil.cu` に `computeCovisibilityBatchKernel` (CUDA カーネル) と `computeCovisibilityBatch` (host 関数) を新規追加, `CUDAImageUtil.h` に宣言を追加. `Bundler.cpp:506-517` の `normal_orientation_nearest` 分岐を, OMP 並列 CPU ループから pose 配列構築 + 1 回の batched GPU 呼び出しに置換した. `computeCovisibilityBatch` はカーネル完了後に `cudaMemcpy` (DeviceToHost, 非 async) で結果を回収しており, これが暗黙的な同期点になっている.
  - **ROI について**: CPU 版・naive GPU 版は `fA->_roi` で走査範囲を絞っていたが, batched 版は ROI 引数を受け取らず画像全体を走査する. ただし `bundlesdf.py:547` で `roi = [0,W-1,0,H-1]` と常にROIが画像全体に設定されているため, 実質的な計算範囲は変わらないことを確認済み. stride (2) と計算式が CPU 版と一致することも確認済み.

## EfficientLoFTR の速度差が小さかった理由

マッチャー段単体では eloftr が 21.8% 速い (61.8ms vs 79.0ms) が, フレーム全体では 8.5%, 壁時計では 4.3% まで縮む.
理由は 4 つある.

1. **マッチャーはフレーム予算の少数派である**. 定常 median 163.5ms のうちマッチャー段は 61.4ms しかなく, 段単体の差はフレーム全体では希釈される (アムダールの法則).
2. **入力が論文のベンチより小さい**. `feature_corres.resize: 400` により 400×400 のグレースケールで推論しており, 論文ベンチ (640 級以上) より小さい. この規模では GPU のカーネル起動と同期のオーバーヘッドが支配的になり, 計算量の差が時間の差に現れにくい. さらに 400 は 8 で割り切れるため旧 LoFTR はパディング不要だが, eloftr だけ 416×416 への +8% のパディングを払っている.
3. **精度優先の設定で動かしている**. 現在は full 設定 + autocast であり, 論文の最速値は opt 設定 (skip_softmax + fp16matmul) のものである. full 設定ではマッチャー単体でも論文の 2.5 倍は出ない. opt 設定への切替は改善項目 2 に含めた.
4. **壁時計は NeRF 律速である**. 同期待ちが壁時計の 52.7% を占め, マッチャーの速さと無関係に全体を支配している.

この差の縮み方は裏返しに読める.
改善が進んでマッチャーの占有率が上がるほど, eloftr の効き幅は拡大する (定常 110ms 時代なら段差 17ms は約 15% に相当する).
既定採用の確定は精度比較 (HO3D の ADD/ADD-S) を待つとしていたが, 2026-07-03 に比較を完了し確定した.
SM1 (898 フレーム, n=895) で eloftr が ADD/ADD-S/ADD_AUC/ADDS_AUC の全 4 指標で loftr を明確に上回った (ADD mean 2.20cm vs 2.77cm, ADD_AUC 78.10% vs 72.39% など. 詳細は `notes/TODO.md` 完了項目参照).
既定バックエンドを eloftr とする根拠が得られ, 改善項目 2 の「マッチャーの opt 設定への切替」(eloftr 前提で議論している項目) の前提も確定した.
ただし SM1 単一動画・単一 seed での比較であり, 他動画での再現性は未確認である.

## プロセス構造 (調査済みの事実, 計測の前提)

- 2 プロセス構成である. メイントラッキング (Python + my_cpp, 同一プロセス) と NeRF ワーカー (`multiprocessing.Process`, spawn). GUI プロセスはベンチ (use_gui=0) では起動しない.
- プロセス間通信はすべて `multiprocessing.Manager` 経由 (p_dict, kf_to_nerf_list, Lock). zmq の 3 ポート (port, seg_port, nerf_port) はこの経路では未使用 (ソケット接続のみで送信なし).
- C++ の `Bundler::runNerf` はどこからも呼ばれない dead code である (実体は Python 側の run_nerf ワーカー). REVIEW_findings #2 の zmq memcpy はこの dead code 内にあり実害は低い.
- C++ の `Utils::Timer` はインスタンス化されておらず, `-DTIMER=1` にしても出力はない. C++ 内訳の計測には Timer の挿入が別途必要.
- C++ 呼び出し (optimizeGPU, runRansacMultiPairGPU, Frame 構築など) は Python の 1 行呼び出しとして境界が切れるため, C++ を触らずに塊単位の時間は Python 側計測 (perf_logger.py) で取れる. 内訳は取れない.
